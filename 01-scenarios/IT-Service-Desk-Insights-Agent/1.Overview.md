# IT Service Desk Insights Agent — Overview

## Scenario Overview

**Scenario Type**: IT Service Management (ITSM) / Employee Support
**Agent Type**: Copilot Studio agent powered by the GitHub Copilot harness; read-only Agent Builder reference retained
**Primary Tools**: ServiceNow, Nexthink APIs, Microsoft Dataverse for Dynamics 365 Customer Service, Office 365 Users, agent-scoped skills and workflows
**Complexity**: Intermediate for knowledge-only; advanced for investigation and controlled actions
**Status**: Blueprint and 17 skill definitions available; tools, connections, and workflows require tenant implementation

This scenario has two implementation paths:

| Path | Purpose | Runtime |
|---|---|---|
| **A - Knowledge and Insights** | Read-only KB and service catalog answers in Microsoft 365 Copilot | Agent Builder declarative agent / Copilot chat harness |
| **B - Investigation and Resolution** | Bounded diagnosis, optional ticket/case actions, and requester-initiated closure | GitHub Copilot harness **inside Microsoft Copilot Studio** |

**Path B is the target for the expanded scenario.** It is one agent with capabilities attached
only to that agent, not an organization-wide skill deployment. Path A remains a lightweight
reference; deploying both agents is not a prerequisite.

The agent can answer a knowledge question, inspect live incident and device evidence, choose
the next approved diagnostic step, and create a support record if the issue remains unresolved.
Each action is independently enabled. Allowing ticket creation does not imply permission to
update, annotate, attach files to, or close an existing ticket.

**Routing is backend-owned.** Creating a ServiceNow incident or Dynamics case hands the record
to existing backend processes; the agent does not choose an assignee, owner, or queue.
**Closure is requester-only:** the user must explicitly ask to close their
own record, and the backend must authorize the supported requester-side transition.

---

## Problem Statement

Service desk teams and their business stakeholders sit on years of ticket history and hundreds
of knowledge articles, and can rarely answer simple management questions without a data
engineering project:

- **Answers depend on who you ask.** The same question asked twice returns a good answer once
  and "I couldn't find that" the next time.
- **Investigations restart at every handoff.** Employees repeat symptoms and attempted fixes
  when support moves between knowledge, diagnostics, and case-management systems.
- **Knowledge alone cannot diagnose a device.** An article cannot establish the current
  connectivity, crash history, or execution result on the affected endpoint.
- **Knowledge is siloed.** Employees search ServiceNow separately from SharePoint, and neither
  search understands the other's content.
- **Access control gets in the way.** ITSM knowledge bases are heavily segmented (HR-scoped
  articles, region-scoped articles, restricted runbooks). Any Copilot experience over that
  content has to honour those rules exactly, or the project stops.

---

## Solution Summary

In Path A, ServiceNow Knowledge and Catalog Copilot connectors index articles and catalog
items into Microsoft Graph with permission trimming. **They do not provide incident records
or user feedback.** Ticket sentiment, ticket themes, and feedback analysis require a separately
authorized source; the baseline must decline those requests rather than infer them from KBs.

In Path B, the harness orchestrates knowledge, agent-scoped skills, and narrowly exposed tools.
Skills describe procedures; connectors provide connectivity; workflows/API policies authorize
and execute operations. The [capability matrix](0.Resources/Capability-matrix.md) defines the
required skill, tool, connector action, prerequisites, and dependencies for each operation.
The [Skills folder](0.Resources/Skills/README.md) contains one standalone instruction
definition per capability. The skills assume configured tools and focus on execution;
deployment prerequisites remain in the matrix and runbook.

Office 365 Users **Get my profile (V2)** supplies the shared `GetMyProfile` tool for
current-user details and an optional language fallback. Its result is reused across skills
in the same conversation; it does not replace backend requester or device-access checks.

The expected benefit is less repeated diagnosis and a more complete handoff, not guaranteed
resolution or inherently better search. Multilingual answers and ticket creation are not
exclusive to the new harness. Live data and write-back depend on the tools that are enabled.

### Key Capabilities

| Capability | Description |
|---|---|
| Grounded knowledge | KB and catalog answers with source references; available in both paths |
| Adaptive diagnosis | Path B reads authorized ServiceNow/Nexthink evidence and selects a bounded next step |
| Capability-level controls | Separate creation, descriptive updates, internal notes, attachments, diagnostic execution, remediation, and requester closure |
| Evidence-rich handoff | Optional Dynamics 365 Customer Service case creation with the investigation context; backend handles routing |
| Requester-only closure | Separate ServiceNow/Dynamics capabilities for an explicit request to close the requester's own record |
| Permission enforcement | Connector ACLs for indexed knowledge; record/device authorization and action policies for live tools |
| Multilingual support | User-language conversation while preserving exact errors, identifiers, and the backend's agreed handoff language |

---

### How Path B Works

1. Reuse or retrieve the current user's profile when needed, then establish the affected
   service/device and explicit time window without repeating known intake questions.
2. Retrieve permitted knowledge and live evidence using enabled capabilities.
3. Evaluate the observations; run another approved diagnostic or remediation only if enabled.
4. Verify execution results. Pending, failed, and unknown outcomes are not successful fixes.
5. If unresolved, create a ticket/case or provide a manual handoff, according to the profile.
6. Close a record only following an explicit request from its verified requester and a
   successful backend-authorized closure. A successful diagnostic or fix never closes it.

| Outcome | Description |
|---|---|
| 📉 Deflect tier-1 tickets | Employees self-serve knowledge and catalog answers from the Copilot they already use |
| Reduce repeated diagnosis | Carry observed symptoms, diagnostic results, and attempted fixes into the support record |

## In Scope / Out of Scope

### ✅ In Scope

- Path A connector deployment, declarative-agent configuration, and permission validation
- Path B agent-scoped skills with independent tool/action enablement
- ServiceNow KB/catalog reads, incident reads/creation, and optional constrained mutations
- Nexthink telemetry reads, separately enabled diagnostic collection and approved remediation
- Dynamics 365 **Customer Service** case reads/creation and optional descriptive updates
- Requester-initiated closure of the requester's own ServiceNow incident or Dynamics case,
  where supported by the backend's self-service lifecycle
- Multilingual support, bounded investigation, permission tests, and capability ON/OFF tests

### ❌ Out of Scope

- **Agent-driven routing or assignment**, during creation or later: no routing skill/tool,
  queue selection, ownership change, or assignment-group override. Backend teams own this.
- **Administrative closure, closure on behalf of another requester, or autonomous closure.**
  Read/update access is not requester identity. Closing one record never implicitly closes
  a linked record.
- ERP integrations, Finance/Supply Chain operations, and GitHub engineering support
- Record deletion, catalog ordering, arbitrary remote scripts, or unrestricted CRUD tools
- Writing through an alternative tool when the corresponding capability is disabled
- Numeric ticket analytics (counts, MTTR, SLA breach rates). Use Power BI over the ServiceNow
  data warehouse. Retrieved samples are not the full ticket population.
- Live ticket status in **Path A**; **Path B** requires an enabled live read tool
- Replacing the ServiceNow Virtual Agent for customer-facing support.

## Knowledge Sources Used

These are the Path A sources. Path B reuses approved content through a validated knowledge
path and adds live tools; an existing Graph connection is not automatically migrated.

| Source | Content | Connector |
|---|---|---|
| ServiceNow Knowledge Base(s) | How-to articles, policies, runbooks, FAQ | ServiceNow Knowledge (synced) |
| ServiceNow Service Catalog | Requestable items and their descriptions | ServiceNow Catalog (synced) |
| SharePoint IT site (optional) | Policy documents not maintained in ServiceNow | Native SharePoint knowledge |

> 📌 Both ServiceNow connectors are deployed from **Microsoft 365 admin center → Copilot →
> Connectors**. Article-level and knowledge-base-level user criteria are carried into the
> Graph index, so retrieval is security-trimmed per user.

Path B adds ServiceNow incident APIs, Nexthink APIs, and optional Dynamics Customer Service
cases. Their identities, permissions, and freshness are separate from the indexed KB ACLs.

## What Actually Goes Wrong

Retain the Path A retrieval checks and add the Path B operation checks:

| Symptom | Root cause | Where it is handled |
|---|---|---|
| Same question answers correctly, then fails minutes later | Inspect retrieval, permissions, and citations; do not assume a single cause | [3.Runbook.md](3.Runbook.md) — Path A, Phase 4 |
| Agent replies in the wrong language | Instructions state the rule once, in prose, competing with the knowledge base language | Phase 3, instruction block |
| Agent cites an article the user cannot open | Advanced (script-based) user criteria evaluated with the **Simple** flow | Phase 1, connector flow selection |
| "List articles from last 7 days" returns nonsense | Relative date reasoning over indexed metadata is unreliable — anchor on explicit dates | Phase 3 + [4.Sample-prompts.md](4.Sample-prompts.md) |
| Wrong or truncated links returned | `AccessUrl` default expression doesn't match the portal URL format the organization uses | Phase 1, property customization |
| A disabled update still executes | Skill removed but generic action or alternate workflow remains exposed | [Capability matrix](0.Resources/Capability-matrix.md) — execution controls |
| Ticket creation loses investigation detail | Native Create Record description limitation; a hidden update is not a create-only solution | Runbook — Step B-2 |
| A case is created with an agent-selected owner | Creation tool accepts backend-owned routing fields | Architecture — routing boundary |
| A colleague can close someone else's case | Closure checks write access or owner instead of verified requester identity | Runbook — Step B-5 |
| Nexthink reports accepted but the device is unchanged | Execution is pending/offline; the request was mistaken for completion | Runbook — Step B-3 |
