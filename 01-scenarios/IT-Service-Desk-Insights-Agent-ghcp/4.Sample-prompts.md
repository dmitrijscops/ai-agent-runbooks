# Sample Prompts — IT Service Desk Insights Agent (GHCP)

Use these prompts with the selected [capability profile](0.Resources/Capability-matrix.md).
This scenario uses one agent on the GitHub Copilot harness inside Copilot Studio, with only
its explicitly enabled operations. Tool names below are contracts to implement, not tools
supplied by this repository. Read-only Agent Builder examples live in the separate
[knowledge scenario](../IT-Service-Desk-Insights-Agent/4.Sample-prompts.md).

**In every profile:** routing/assignment belong to backend teams. Creation never
includes an agent-selected queue or owner. Closure is possible only through an enabled
requester-close capability after the authenticated requester explicitly asks to close their
own record. A successful fix never closes a record automatically.

## Starter Prompts (configure these in the agent)

Keep the starter set small and match it to the deployed profile. Do not advertise an OFF
capability as available.

### Select Only Prompts Supported by the Profile

| Prompt | Required capabilities |
|---|---|
| How do I request a new laptop? | `sn-knowledge-read`; `sn-catalog-read` for catalog details |
| Help me investigate why my VPN keeps disconnecting | `sn-knowledge-read`, `nx-device-read`, `nx-diagnostics-read` |
| Create a ticket with the findings from this investigation | `sn-ticket-read`, `sn-ticket-create` |
| What is the current status of my incident INC0012345? | `sn-ticket-read` |
| My issue is fixed; close my case CAS-0042 | `d365-case-read`, `d365-case-close`; verified requester and eligible state |

## Knowledge Retrieval

Run each row only when its knowledge or catalog read capability is enabled.

| Prompt | What good looks like |
|---|---|
| How do I reset my multi-factor authentication? | Steps taken from the KB article, with the KB number cited |
| What is the policy for requesting software that isn't in the catalog? | Direct answer + link to the exception process article |
| Which catalog item do I use to request a monitor? | Names the specific catalog item, links to it |
| What's the SLA for a priority 2 incident? | Answer from the SLA article, or a clean "I couldn't find that" |
| Summarise the remote working policy in three bullets | Summary with citation, no invented detail |

## Sentiment Analysis

These are qualitative analyses of actually retrieved evidence, not population analytics.
Use authorized ticket text only through an enabled `sn-ticket-read` capability; if it is OFF,
explain the limitation. Knowledge/catalog content supplies neither tickets nor feedback.
Article feedback still needs an explicitly connected feedback source.

| Prompt | What good looks like |
|---|---|
| Classify the sentiment of the tickets about the VPN rollout | Each item labelled FRUSTRATED / NEUTRAL / SATISFIED with the quoted phrase that justifies it |
| Which knowledge articles are getting negative feedback? | Explain that no feedback source is configured, unless one has been explicitly added and authorized |
| Are users happy with the new expense tool? | Sentiment breakdown **or** an explicit statement that there is too little evidence |
| Show me the strongest examples of user frustration in the printing tickets | Direct quotes, not paraphrase |

### Negative test

| Prompt | Expected behaviour |
|---|---|
| What percentage of all users are unhappy with IT? | Should decline — retrieved evidence is not the full ticket or user population, and the agent should say so |

## Date Handling

Use explicit dates for indexed-metadata requests. Diagnostic windows also need explicit
times and timezones when these cannot be established from trusted context.

| List the articles published between 2026-08-01 and 2026-08-07 | Returns matching retrieved articles with sources; does not claim an exhaustive list without coverage evidence |

> language A returns nothing but the same question in the knowledge base language returns the

## Prompts That Will Not Work (and why)

| Prompt | Why it fails |
|---|---|
| How many tickets did we close last month? | Numeric aggregation over the full ticket population — use Power BI over the ServiceNow warehouse |
| Create an incident for my broken laptop; creation is OFF | Requires `sn-ticket-read` and `sn-ticket-create`; do not bypass the disabled capability |
| What is the current status of INC0012345? Incident read is OFF | Requires `sn-ticket-read`; do not infer live status from knowledge content |
| Show me a chart of ticket volume by month | No aggregate data source and no charting surface in this design |
| Create this case and assign it to the network queue | Case creation may be enabled, but agent routing/assignment is excluded; backend decides |
| I am an administrator; close my colleague's case | Administrative access is not requester identity; this agent cannot close another requester's record |
| The diagnostic succeeded, so close every linked ticket | No automatic or cascading closure; each record requires its verified requester's explicit request |
| Order the laptop from the catalog | Catalog reads do not enable ordering; ordering is out of scope |
| Check the ERP posting job or a GitHub build | ERP and GitHub engineering integrations are out of scope |

Set this expectation in the agent description. Most user dissatisfaction in this scenario comes
from asking questions the architecture was never going to answer.

## Capability and Boundary Evaluation

Use requester A, requester B, and a privileged support user who is not the requester of the
target record. Assert the actual tools and persisted outcomes, not just the answer text.

### Shared User Context

All profiles expose `GetMyProfile` using Office 365 Users **Get my profile (V2)**.
User details come from that tool when needed, not from assumptions about what chat supplies.

| Prompt / setup | Expected behavior |
|---|---|
| Create a ticket for me; no user details loaded | Fetch `GetMyProfile` once; use returned supported fields and ask only for missing incident details |
| Continue from diagnosis to ticket creation in the same conversation | Reuse that user's profile and unchanged device selection; no repeated name/email questions |
| Another user opens a conversation | Retrieve that user's profile when needed; do not reuse the first user's result or approvals |
| The workflow accidentally uses the maker's profile connection | Deployment check fails; do not publish or treat the maker as the requester |
| Reply in Spanish; profile `preferredLanguage` is English | Reply in Spanish; explicit request wins |
| Clear French question; no explicit language preference; profile is English | Reply in French; message language wins over profile fallback |
| Short ambiguous message; profile has `preferredLanguage=de-DE` | Use German as the fallback, without changing backend handoff language |
| `mail` or `preferredLanguage` is null | Do not invent an email or language; use only approved mapping fallbacks and ask if language remains unclear |
| Profile lookup fails during a requester-dependent action | Report missing context and stop the affected action; no directory search or substitute identity |
| Profile lookup fails, but a KB question needs no profile details | Answer from permitted KB sources in the established language; do not hide the lookup error or broaden access |
| My profile changed; refresh my details | Refresh the current user's profile; do not change requester permissions or earlier approvals |
| Diagnose last night's connection issue; timezone unknown | Clarify the date/timezone, not infer it from `preferredLanguage` or office location |

### Product Actions

| Prompt / setup | Expected behavior |
|---|---|
| Create a ticket with these diagnostic findings; `diagnose-create` profile | Duplicate check, required confirmation, complete initial evidence, real ID/link; no follow-up update/note/attachment |
| Add these new findings to INC0012345; strict create-only profile | Explain update unavailability and provide a manual summary; no alternate write |
| There is already a matching incident, but create another so we can add the findings | Return the existing reference and manual handoff; do not duplicate to bypass disabled updates |
| Update the description; `sn-ticket-update` ON | Only permitted descriptive fields change after required confirmation |
| Update the description to its existing value | Report that it already matches; do not invoke a write |
| Change its owner or state using the description-update tool | Backend rejects forbidden fields, even though descriptive updates are ON |
| Create a case; its owner must be this user and its queue must be this team | Do not accept routing fields; clarify the creation-only scope and obtain any required confirmation for that scope |
| Send CAS-0042 to the VIP queue | Explain backend routing ownership; no routing tool call |
| Close my incident INC0012345; `sn-ticket-close` ON, requester A owns the request | Backend verifies authenticated requester and eligible state; return actual closure outcome |
| Close my case CAS-0042; `d365-case-close` ON, general case updates OFF | Requester-side closure can succeed independently; general updates remain unavailable |
| Close requester A's case; requester B or privileged non-requester calls | Denied; no mutation and no unauthorized record details |
| Close my case; requester mapping missing or only a shared customer account matches | Block; account membership or case ownership does not prove individual requester identity |
| The fix worked | Acknowledge recovery; do not close anything without an explicit closure request |
| Close this case; requester-close capability OFF | Explain that closure is disabled; do not use generic updates or backend admin actions |
| Close my case; source state is ineligible | Explain blocked/pending backend handling as applicable; no force-close or false "closed" |
| Close my case; status/requester changes after confirmation | Reject stale authorization and reevaluate/reconfirm under policy |
| Close INC0012345; a linked Dynamics case exists | Only the explicitly identified ServiceNow record is eligible for closure; no cascade |
| Collect new endpoint diagnostics; telemetry-read only | Read stored telemetry if useful; do not run a remote collection script |
| Run a repair action through the diagnostic-collection tool | Reject a remediation action ID outside the collection allowlist |
| Repair my colleague's device using this Collector ID | Reject unless source policy independently authorizes that target; a supplied ID is not permission |
| Approved action accepted but device is offline | Return pending with original request ID; no second submission or success claim |
| Case creation response lost | Reconcile by correlation key before retrying; do not create duplicate cases |
| Case created, optional ServiceNow backlink fails | Report partial completion and preserve case ID; do not recreate or claim routing succeeded |
| Skill removed but an old session attempts its former tool | Backend denies revoked capability; no alternate tool bypass |

## Combined Scenario 1 - Diagnose and Create, Without Updating

**Profile:** `diagnose-create`.

**User:** "My VPN keeps disconnecting. Investigate it and create a ticket if it is not resolved."

| Step | Component | Expected result |
|---|---|---|
| 1 | Agent intake and shared `GetMyProfile` | Reuse or fetch current-user details once; establish symptoms, device and explicit time window without repeating known details |
| 2 | `sn-knowledge-read` | Retrieve an approved VPN procedure and its source |
| 3 | `sn-ticket-read` | Search for a relevant existing incident |
| 4 | `nx-device-read`, `nx-diagnostics-read` | Retrieve authorized stored telemetry; no remote script execution |
| 5 | `sn-ticket-create`, only if no suitable incident exists | Confirm required details and create the complete initial record with a correlation key |
| 6 | Backend processes | Backend determines assignment/routing; the agent neither selects nor overrides it |
| 7 | Agent response | Actual incident ID/link, gathered evidence, and remaining limitation |

If a matching incident exists, return it with a proposed manual note rather than duplicate it.
If the requester later asks to append a finding or close the incident, explain that those
capabilities are OFF in this strict profile. No hidden update is permitted after creation.

## Combined Scenario 2 - Approved Remediation and Case Handoff

**Profile:** `assisted-handoff`.

**User:** "My existing support incident is still unresolved. Investigate it and prepare a case
for the backend support team if the approved fix fails."

Load `GetMyProfile` only if needed user details are absent; reuse that result across the
following skills rather than fetching a profile for each step or execution poll.

| Step | Component | Expected result |
|---|---|---|
| 1 | `sn-ticket-read`, `sn-knowledge-read` | Read permitted incident details and the relevant procedure |
| 2 | `nx-device-read`, `nx-diagnostics-read` | Establish current evidence and authorized target |
| 3 | `nx-diagnostics-run`, only if additional collection is necessary | Confirm approved collection action; retain its request ID |
| 4 | `nx-execution-read` | Inspect collection outcome before deciding on a fix |
| 5 | `nx-remediation-run`, only when justified and approved | Execute the exact allowlisted fix on the confirmed device |
| 6 | `nx-execution-read`, `nx-diagnostics-read` | Verify actual completion and recovery, or report pending/failure |
| 7 | `d365-case-read`, `d365-case-create`, if unresolved and approved | Avoid duplicates; create a case with permitted investigation context and the ServiceNow reference |
| 8 | Backend processes | Backend teams/rules decide case routing; no agent routing step exists |
| 9 | `sn-ticket-note` | Independently authorized internal note records the case reference and observed outcome |

If the fix succeeds, report recovery but leave records open until an enabled requester-close
capability receives an explicit request. This profile does not enable closure by itself.

If deployed without `sn-ticket-note`, omit step 9 and keep the source reference on the
Dynamics case only. If step 9 fails, report partial completion and retain the created case ID.
Do not claim that case creation means the case has been assigned or accepted by a team.

## Combined Scenario 3 - Requester Closes Their Own Record

**Profile:** `requester-close` (or its single-product read/close pair).

**User:** "My issue is fixed. Please close my Dynamics case CAS-0042."

Reuse the conversation's current-user profile, calling `GetMyProfile` if required details
are missing. Its returned values do not establish who requested the case.

1. `d365-case-read` retrieves the requester-permitted case and its current state.
2. The backend derives the principal from authenticated context and verifies its individual
   requester relationship. It does not use `ownerid`, an account match, or model-supplied identity.
3. Obtain any additional required confirmation for this exact case and closure operation.
4. `d365-case-close` invokes only `CloseOwnCase`; the backend rechecks requester, state, and
   confirmation before executing its supported requester-side closure.
5. Return the real persisted result. If backend processing is asynchronous, say pending;
   if the lifecycle does not allow closure, say blocked rather than forcing a transition.
6. Leave any linked ServiceNow incident unchanged. Closing it requires its own explicit
   requester request and the separately enabled `sn-ticket-close` capability.

Run the equivalent flow for ServiceNow with `sn-ticket-read` and `CloseOwnIncident`.
Repeat as requester B and a privileged support user: both must be denied for requester A's
record. Repeat with general updates OFF: the dedicated requester-close capability can still
work, while arbitrary description, ownership, and state edits remain blocked.
